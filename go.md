# Передача контекста: обучение Go

## Цель обучения

Пользователь изучает Go с нуля до уверенной backend-разработки: пройти собеседование, писать REST API, освоить конкурентность и сделать pet-project. Режим: 1–2 часа в день. Обучение нужно вести небольшими последовательными блоками: объяснение простым русским языком → практическое задание → пользователь присылает код/вывод → code review и следующий блок. Не выдавать весь курс сразу.

## Педагогические особенности

- Пользователь хорошо понимает код после пошагового объяснения, но важно не давать упражнение на конструкцию до её объяснения. Пример: задача реализовать `max` через `if` была дана раньше урока об условиях, что вызвало закономерный вопрос.
- Нужны чёткие указания: какой файл менять, что именно добавить/заменить и зачем.
- При вставке кода в чат Markdown искажает отображение идентификаторов и типов, добавляя видимые `*` вокруг слов. Пользователь подтвердил, что в редакторе указателей там нет. Не следует повторно утверждать, что он использовал указатели, ориентируясь только на такой текст из чата.
- Пользователь предпочитает начинать с малого: прежде чем давать целый table-driven test, полезно отдельно объяснить структуру простого unit-теста.

## Что уже прошли

### 1. База Go и запуск проекта

- `package main`, `func main()`, импорт `fmt`.
- Запуск проекта: `go run .`.
- Модуль (`go.mod`) как единица проекта и зависимостей.
- Форматирование: `gofmt -w .`.
- Статическая проверка: `go vet ./...`.
- Переменные, вывод типа через `:=`, базовые типы `string`, `int`, `bool`.
- Нулевые значения: `0`, `""`, `false`, `nil` для указателей.
- Разница между `fmt.Println` (печатает) и `fmt.Sprintf` (возвращает строку).
- Функции с параметрами и возвращаемыми значениями:

```go
func greet(name string, age int) string
func isAdult(age int) bool
```

- Идиоматичное сокращение булевой функции: `return age >= 18`.
- Стиль имён: `camelCase`, например `stepName`, а не `step_name`.

### 2. Условия и циклы

- `if`, `else`, логические условия типа `bool`.
- Паттерн guard/раннего возврата: после `return` не нужен `else`.
- `for` как единственный цикл Go; варианты с условием и со счётчиком.
- `switch` без выражения для последовательности условий.
- В `switch` не нужен `break`: ветка заканчивается автоматически.

Практика выполнена:

```go
func describeAge(age int) string
func sumTo(n int) int
```

В `describeAge` корректно использована последовательность условий сверху вниз: пенсионер → взрослый → несовершеннолетний → некорректный возраст. В `sumTo` рекомендуется `sum := 0` и `for i := 1; i <= n; i++`.

### 3. Срезы и map

- Срез (`slice`) как динамический список: `[]int{...}`, `append`, `len`.
- Итерация: `for _, value := range slice`.
- `map` как пары ключ–значение: `map[int]string`.
- Безопасное получение из map через `value, ok := m[key]` — comma-ok idiom.

Практика выполнена:

```go
func countAdults(ages []int) int
func getUserName(users map[int]string, id int) string
```

`countAdults` правильно считает только значения `>= 18`. `getUserName` корректно возвращает имя либо строку о том, что пользователь не найден.

### 4. Структуры, методы и указатели

- `struct` для связных данных:

```go
type Task struct {
    ID        int
    Title     string
    Completed bool
}
```

- Метод с value receiver для чтения:

```go
func (t Task) Status() string
```

- Метод с pointer receiver для изменения исходной структуры:

```go
func (t *Task) Complete() {
    t.Completed = true
}
```

- Go автоматически берёт адрес addressable-переменной при вызове `task.Complete()`; явное `(&task).Complete()` обычно не нужно.
- Упрощение булевой проверки: `if t.Completed`, а не `if t.Completed == true`.

Практика выполнена: созданы две задачи, проверен статус до и после `Complete()`.

### 5. Ошибки

- Ошибки возвращаются отдельным значением типа `error`, типичная сигнатура: `func (...) (T, error)`.
- Успех: вернуть объект и `nil`.
- Ошибка: вернуть нулевое значение объекта (`Task{}`) и ошибку.
- Создание ошибки: `errors.New(...)`.
- Ошибку надо проверять сразу: `if err != nil { ... }`.
- Две sentinel-ошибки для валидации задачи:

```go
var ErrInvalidTaskID = errors.New("ID задачи должен быть больше нуля")
var ErrEmptyTaskTitle = errors.New("название задачи не должно быть пустым")
```

- Функция, которую реализовал пользователь:

```go
func createTask(id int, title string) (Task, error) {
    if id <= 0 {
        return Task{}, ErrInvalidTaskID
    }
    if title == "" {
        return Task{}, ErrEmptyTaskTitle
    }
    return Task{ID: id, Title: title, Completed: false}, nil
}
```

- Обсуждали `errors.Is(err, target)` как более устойчивую проверку конкретной ошибки, особенно когда позже используется wrapping через `fmt.Errorf("контекст: %w", err)`.

### 6. Unit-тесты и table-driven tests

- Тестовый файл должен оканчиваться на `_test.go`; имя может быть тематическим, например `errors_test.go`, а не обязательно `main_test.go`.
- Все `.go`-файлы в одной папке с одинаковым `package` собираются вместе. `main.go` нужен только для `go run .` исполняемой программы, а тесты могут запускаться без него.
- Базовая структура теста: подготовить входные данные → вызвать функцию → сравнить результат с ожиданием.
- `t.Fatalf` / `t.Fatal` прекращают текущий тест; `t.Errorf` / `t.Error` фиксируют ошибку и продолжают выполнение.
- Запуск: `go test ./...`.
- `ok learn ...` означает, что пакет успешно собрался и все тесты/подтесты прошли.
- Реализованы и успешно запущены:
  - успешное создание задачи (`TestCreateTaskSuccess`);
  - table-driven test неверного ввода: нулевой ID, отрицательный ID, пустое название.
- В таблице есть поле `wantErr error`; каждый кейс задаёт ожидаемую sentinel-ошибку.
- Рекомендуемая проверка:

```go
if !errors.Is(err, tt.wantErr) {
    t.Errorf("ошибка = %v, ожидали %v", err, tt.wantErr)
}
```

## Текущая точка

Пользователь успешно завершил тесты `createTask` с `wantErr`; последний вывод был:

```text
ok      learn   0.909s
```

Последнее предложенное действие — заменить прямое сравнение `err != tt.wantErr` на `!errors.Is(err, tt.wantErr)`, добавив импорт `errors` в тест. Пользователь ещё не прислал результат этой маленькой правки.

После неё логичное продолжение: организация Go-проекта по пакетам, чтобы логика задач не жила в `package main`. Перед практикой нужно объяснить, что файлы в одной директории образуют пакет, а экспортируемые имена начинаются с заглавной буквы. Затем можно постепенно перейти к интерфейсам, HTTP/JSON, REST API, PostgreSQL, `context`, конкурентности и pet-project.

## Рекомендованный дальнейший маршрут

1. Завершить `errors.Is` и показать короткий пример оборачивания ошибки через `%w`.
2. Пакеты и структура проекта: разделить консольный запуск и доменную логику задач.
3. Интерфейсы: маленький пример, только когда есть реальная потребность в абстракции; подчёркивать принцип Go «простота важнее абстракций».
4. HTTP и JSON: `net/http`, handler, request/response, статусы, JSON-кодирование.
5. REST API для задач: CRUD сначала в памяти.
6. PostgreSQL: `database/sql` и драйвер, миграции, repository без избыточной архитектуры.
7. `context`, middleware, graceful shutdown.
8. Goroutine, channel, mutex, race conditions, запуск `go test -race ./...`.
9. Развитие pet-project, тесты handler/service/repository, линтеры, Docker и собеседования.

## Стиль наставничества

- Писать по-русски, простыми словами, но с правильными терминами и кратким пояснением.
- Предпочитать идиоматичный Go и простые решения.
- После каждого блока давать небольшую практику, ждать код или вывод, делать конкретное code review.
- Не усложнять абстракциями без практической причины.
